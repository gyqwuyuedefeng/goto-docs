````markdown
## Hybrid Execution Agreement

Every plan must include a command template:

```bash
/home/gyq/.local/bin/codex-dp-exec \
  --cd <task-worktree> \
  --prompt-file <prompt-file> \
  --task-id <task-id> \
  --controller-id <codex1-or-codex2> \
  --output-last-message <report-file>
```

Every plan must say that the controller checks:

- `status.json`
- `heartbeat.json`
- `stdout.log`
- `stderr.log`
- `report.md`
- `exit_code`
- implementer report
- `git diff`
- changed files
- test output

The controller must review spec compliance first. Only after spec compliance passes may it review code quality. A task is complete only after both reviews pass.

## Task Requirements

Each implementation task must include:

- Stable ASCII `task_id`, such as `task-003-firelm-backend-tracking-core`.
- Execution mode:
  - `controller inline`
  - `DeepSeek implementer`
  - `DeepSeek implementer + controller重点复核`
- Exact `--cd <worktree>` path.
- Exact files to create, modify, or test.
- Files and behaviors that must not be modified when relevant.
- Complete task context that can stand alone in a DeepSeek prompt.
- Test commands and expected results.
- Commit commands, unless the files are outside any Git repository.
- Report requirements.

## DeepSeek Prompt Requirements

Each task must be detailed enough for the controller to create a prompt containing:

```text
最终报告必须包含：
- status: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
- changed_files: 本任务改动的文件列表
- commits: 本任务产生的 commit hash；没有提交时说明原因
- tests: 实际运行的测试命令和结果
- concerns: 风险、未验证项或需要 controller 判断的问题

执行要求：
- 只能修改本 Task 声明的仓库和文件范围。
- 不得回退用户或其他 agent 的无关改动。
- 不得执行 mvn deploy。
- 不得通过数据库客户端执行写操作。
- 如果计划与代码现状冲突，停止并返回 NEEDS_CONTEXT，不要猜测。
```

## Task 0 Requirements

Task 0 is normally `controller inline`. It must verify:

- Required worktree paths exist.
- Branch names match the plan.
- `git status --short` is understood before any implementation task starts.
- Any required new worktree is created according to project rules.
- `codex-dp-exec` is executable when Hybrid execution is required.

## Recovery Rules

Every Hybrid-ready plan must state:

- If a run is `interrupted`, inspect current `git diff` before retrying.
- Recovery creates a new run for the same `task_id`; do not overwrite the interrupted run.
- If DeepSeek returns `BLOCKED` or `NEEDS_CONTEXT`, the controller decides whether to provide more context, split the task, retry, or escalate to the user.
- Temporary prompt, report, and run directories must not be committed unless the user explicitly asks.

## Old Plan Conversion

When converting an old plan to Hybrid-ready format:

- Preserve valid task intent.
- Add stable ASCII `task_id` values.
- Add worktree paths and execution modes.
- Add prompt/report requirements and controller review gates.
- Add missing test commands or mark the plan blocked until tests are known.
- If paths are stale, tasks are too large, or the old plan depends on missing conversation history, return a readiness issue list instead of pretending the plan is executable.

## Self-Review

Before saving the plan, check:

1. Spec coverage: every approved spec requirement maps to a task.
2. Hybrid readiness: every implementer task has `task_id`, worktree, files, tests, report requirements, and recovery rules.
3. Placeholder scan: no unresolved placeholder markers, vague "handle edge cases", or cross-task shorthand.
4. Type and naming consistency: later tasks use names defined earlier.
5. Scope: tasks are small enough for one DeepSeek implementer turn and one controller review cycle.

3. Inline Execution - Execute tasks in this session using `superpowers:executing-plans`.

Which approach?
```
````
