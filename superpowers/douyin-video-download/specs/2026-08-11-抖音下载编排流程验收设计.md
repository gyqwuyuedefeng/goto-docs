# 抖音下载编排流程验收设计

## 文档状态

- 日期：2026-08-11
- 项目：`douyin-video-download`
- 代码目录：`/mnt/f/IdeaProjects/goto-software/douyin-video-download`
- 主流程：Superpowers，经 Codex Task Orchestrator 保存阶段输出并执行
- 状态：已完成设计确认，待书面复核

## 1. 目标与优先级

本轮首要目标不是建设完整的抖音下载系统，而是用一个真实、边界清楚的小功能验证 Codex Task Orchestrator 的完整流程是否稳定、健壮并符合设计：

1. 正式创建 WorkItem；
2. 保存 Brainstorm、Spec、Plan 的不可变版本；
3. 认领时冻结阶段输出、目标仓库、具体分支与关联历史；
4. Worker 在独立 worktree 中调用 Codex，保留完整脱敏日志；
5. Codex 按 TDD 实现、测试并产生带正确 `Task-ID` 的本地提交；
6. 平台保存结果、改动文件、测试、提交、风险和 Review；
7. 对流程中暴露的问题执行最小修复后继续，最终形成问题清单。

下载器本身只需形成一个可运行、可自动测试的最小垂直闭环，不追求生产级抖音兼容率。

## 2. 方案选择

采用“命令行工具 + 可复用 Python 模块”方案：

- 输入一段抖音分享文字或一个分享链接；
- 提取并校验唯一 HTTP(S) 链接；
- 调用一个边界明确的下载适配器获取公开视频；
- 把视频保存到指定目录；
- 以结构化 JSON 输出成功或失败结果。

不采用完整网页服务，因为页面、会话和并发控制不是本次编排流程验收的必要条件；不采用纯模拟任务，因为它不足以验证 Codex 面对陌生真实项目时的设计和执行能力。

## 3. 下载器最小架构

### 3.1 组件

- `cli`：解析命令行参数并输出 JSON；不包含站点解析细节。
- `share_link`：从分享文字中提取唯一 URL，只允许抖音受控域名。
- `downloader`：封装实际提取与下载工具，返回标题、视频 ID、目标文件和字节数。
- `models/errors`：定义小型结果模型和可稳定判断的错误码。

优先使用成熟的 `yt-dlp` 作为下载适配器，不自行复制抖音签名算法。适配器必须可替换，以便自动化测试使用本地假实现，不访问真实抖音网络。

### 3.2 使用方式

示例接口：

```bash
uv run douyin-video-download \
  "8.12 复制打开抖音 https://v.douyin.com/example/" \
  --output-dir ./downloads
```

成功时退出码为 0，并输出包含 `status`、`video_id`、`title`、`output_path`、`bytes` 的 JSON。失败时使用非零退出码，并输出不包含 Cookie、下载地址或异常堆栈原文的稳定错误码与中文提示。

## 4. 安全与外部依赖边界

- 只处理用户有权访问的公开、无 DRM 视频；不绕过私密、登录、地区或权限限制。
- 默认无需登录；若站点要求验证，仅允许通过仓库外标准 Cookie 文件显式提供。
- 私钥、Cookie 和其他秘密不得进入 Git、Codex Prompt、应用日志、测试证据或平台数据库。
- 不实现自建登录、验证码处理、反爬签名算法、代理池或浏览器自动化。
- 真实抖音访问失败必须区分为外部站点限制、输入问题和本地实现缺陷，不得把外部风控伪报为编排器失败。

## 5. 错误处理

首版至少稳定处理：

- 没有 URL；
- 同时出现多个 URL；
- 非 HTTP(S) URL；
- 非抖音域名；
- 输出目录不可写；
- Cookie 文件缺失、位于仓库内或不是普通文件；
- 网络超时、视频不可用或提取器失败；
- 下载结果为空或不是预期媒体文件。

所有失败均须清理临时文件，且不得留下看似成功的零字节目标文件。

## 6. 测试策略

### 6.1 稳定自动化

- 单元测试：分享文字解析、唯一链接、域名白名单、输出文件名和错误映射。
- 集成测试：使用本地 HTTP 假服务与假下载适配器验证成功下载、超时、空文件、清理和 JSON 输出。
- CLI 验收：在临时目录运行真实 CLI 进程，验证退出码、标准输出和目标文件。
- 安全断言：Cookie 内容不出现在输出、日志、提交或测试证据中。

默认自动化测试不得依赖抖音在线状态，以免外部风控造成不可重复结果。

### 6.2 可选真实冒烟

在稳定自动化全部通过后，可选择一个公开分享链接执行一次真实冒烟测试。成功则记录脱敏元数据与文件检查；失败则记录错误类别和环境，不阻断编排器闭环，除非失败源于 Prompt、worktree、日志、提交、状态机或恢复机制。

## 7. 编排器验收观察点

- 页面和 API 中能找到本 WorkItem 及完整阶段版本。
- 认领快照中的 Brainstorm、Spec、Plan 与批准版本逐字节一致。
- Worker Prompt 包含任务 ID、目标、阶段内容和关联历史摘要。
- Codex 不直接修改 `main`，不提前提交，不访问未授权目录。
- RED、GREEN 和最终测试证据都能从日志或结果追溯。
- 本地提交只包含任务范围文件，主题为中文，并带当前 ExecutionTask ID。
- 中途失败时 Attempt 不被静默覆盖；恢复原因、次数和结果可见。
- 最终 Review 前任务不能变为完成；批准后状态、结果和审计一致。

发现流程缺陷时，只修复能够复现且阻断或削弱本次闭环的问题；不新增分布式调度、通用插件系统、LLM Judge 或新的治理层。

## 8. 验收标准

1. 平台完成 WorkItem → 三阶段输出 → 认领快照 → Attempt → 结果 → Review 的真实链路。
2. 目标仓库产生一个隔离任务提交，提交包含正确 `Task-ID`，`main` 在人工批准前保持不变。
3. 下载器稳定自动化测试全部通过，且至少覆盖一个成功路径和主要失败路径。
4. 完整日志可分段读到结尾，完整性校验通过，秘密泄露为 0。
5. 最终报告列出本次发现的编排器问题、根因、修复和剩余风险。
6. 若真实抖音冒烟受外部限制，仍能基于稳定自动化和完整编排事实判定平台流程；不得伪造真实下载成功。

## 9. 明确不做

- 网页界面、数据库、下载历史、批量下载、队列或多用户；
- 私密视频、登录绕过、去水印、转码、剪辑或其他站点；
- 为未来需求预建插件框架、分布式 Worker 或复杂下载调度；
- 把真实站点不稳定性加入默认 CI；
- 为了证明治理材料而增加新的治理材料。
