# 通用任务执行批次幂等修复设计

## 背景

通用任务链路已经完成 Redis Stream 长任务租约、真实终态、完成事件、ACK 与日志可观测性修复。现在线上观察到同一页面连续执行同一个通用任务时，第二次任务会被直接跳过：

```text
任务已完成，无需重复创建：consumerName=group:common_task_service, idempotencyKey=common-task:13:merge-image-dd8c29b1-fe52-43e0-98ff-98fc9efbd1e4, status=SUCCEEDED
任务已处于终态，跳过执行：jobId=19, status=SUCCEEDED
```

当前 `CommonTaskCommandStreamConsumer` 使用 `common-task:{taskType}:{commonNoticeUUID}` 构造 `idempotencyKey`。而拼图、图片转换、Excel 转换等前端页面会把 `commonNoticeUUID` 作为页面级 WebSocket 通知路由，在同一个页面生命周期内持续复用。结果是第一次执行成功后，`stream_job_execution` 中的终态记录会阻止后续点击重新执行。

本设计目标是拆分“前端通知路由”和“后台执行幂等”两个概念：同一个页面里用户第二次点击“生成/执行”时，必须创建一次新的后台执行；同一条 Redis Stream 消息重试时，仍必须保持幂等，不重复执行。

## 目标

1. 同一页面内重复点击通用任务执行按钮时，即使 `commonNoticeUUID` 不变，也必须创建新的后台执行记录并重新执行。
2. `commonNoticeUUID` 继续作为前端 WebSocket 页面通知路由，不改变现有页面消息过滤方式。
3. Redis Stream 同一条消息重复投递、PEL 恢复或租约接管时，仍使用稳定幂等键避免重复执行。
4. 兼容历史 Redis Stream 消息：没有新字段的旧消息仍可按旧规则消费。
5. 不改变 `stream_job_execution` 表结构和唯一约束，避免引入迁移风险。

## 非目标

1. 不重写 Redis Stream starter、ACK 机制、租约机制或完成处理器整体流程。
2. 不改变前端 WebSocket 路由协议，不要求前端每次点击刷新 `commonNoticeUUID`。
3. 不清理历史 `stream_job_execution` 终态记录。
4. 不在本次设计中扩展任务取消、进度查询或多任务列表能力。

## 核心设计

新增通用任务执行批次标识 `executionId`。它表示“本次后台执行批次 ID”，每次用户提交通用任务都应不同。

字段职责如下：

```text
commonNoticeUUID：前端页面通知路由，同一页面可复用。
executionId：后台执行批次标识，每次提交应唯一，用于 Job Ledger 幂等。
```

新的幂等键规则：

```text
idempotencyKey = common-task:{taskType}:{executionId}
businessId     = commonNoticeUUID
```

历史兼容规则：

```text
如果 executionId 为空：
  idempotencyKey = common-task:{taskType}:{commonNoticeUUID}
```

这样可以同时满足两类语义：

- 用户同一页面再次点击：发布端生成新的 `executionId`，消费者创建新的 `stream_job_execution` 记录，任务重新执行。
- 同一 Redis Stream 消息重试：消息 payload 中的 `executionId` 不变，消费者命中同一账本，保持幂等。

## 组件变更

### CommonTask

在 `common/src/main/java/com/freedom/model/CommonTask.java` 新增字段：

```java
private String executionId;
```

字段注释需要说明它是后台执行批次 ID，不是前端页面通知路由。现有序列化使用 Jackson/Lombok 默认机制，新增字段可随 Redis Stream payload 一起传递。

### CommonTaskStreamPublisher

`system/src/main/java/com/freedom/util/CommonTaskStreamPublisher.java` 作为通用任务统一发布入口，发布前负责兜底生成 `executionId`：

```text
如果 commonTask.executionId 为空白：
  commonTask.executionId = UUID.randomUUID().toString()
否则：
  保留调用方传入的 executionId
```

保留调用方传入值是为了支持未来显式重试同一次业务提交时复用同一个执行批次。当前拼图、图片转换、Excel 转换、数据处理等调用方无需逐个手动生成，统一由发布器兜底，降低遗漏风险。

### CommonTaskCommandStreamConsumer

`task/src/main/java/com/freedom/bean/mq/redisstream/CommonTaskCommandStreamConsumer.java` 调整 `buildIdempotencyKey`：

```text
taskType = commonTask.taskType 或 unknown
executionId = trim(commonTask.executionId)

如果 executionId 非空：
  返回 common-task:{taskType}:{executionId}
否则：
  返回 common-task:{taskType}:{commonNoticeUUID 或 no-uuid}
```

`resolveBusinessId` 仍返回 `commonNoticeUUID`，因为它描述的是前端页面上下文或任务上下文，而不是执行批次。

完成上下文 `CommonTaskCompletionContext.idempotencyKey` 继续保存消费者构造出的同一个幂等键。注册表 key 继续使用：

```text
group:common_task_service:{idempotencyKey}
```

### CommonTaskRedisCompletionHandler

完成处理器目前也通过 `buildIdempotencyKey(commonTask)` 查找注册表上下文。它必须与消费者使用完全一致的规则：

```text
优先 executionId，缺失时降级 commonNoticeUUID。
```

如果消费者和完成处理器规则不一致，会出现任务已提交但完成时找不到上下文的问题，因此这部分需要补充回归测试。

## 数据流

```text
前端提交任务
→ system 构造 CommonTask，保留 commonNoticeUUID
→ CommonTaskStreamPublisher 生成或保留 executionId
→ Redis Stream 写入带 executionId 的 CommonTask
→ task 消费消息
→ CommonTaskCommandStreamConsumer 用 executionId 构造 idempotencyKey
→ JobLeaseService 按 consumerName + idempotencyKey 创建或读取账本
→ 后台线程执行 R/业务逻辑
→ 完成处理器按同一 idempotencyKey 找上下文、写终态、发通知、ACK
→ system 通知消费者按 commonNoticeUUID 推送到前端页面
```

## 错误处理

1. Job Ledger 创建失败：保持现有行为，不写终态、不通知、不 ACK，让消息留在 PEL 等待恢复。
2. 同一 Redis Stream 消息重复投递：payload 内 `executionId` 不变，命中同一账本，不重复执行。
3. 同一页面再次点击：发布器生成新的 `executionId`，创建新账本并重新执行。
4. 历史消息无 `executionId`：按旧 `taskType + commonNoticeUUID` 幂等键处理，保证兼容。
5. `executionId` 为空白字符串：按缺失处理，由发布器生成；若绕过发布器直接进入消费者，则消费者降级旧规则。
6. 通知发布失败：保持既有完成处理器语义，不 ACK，等待恢复链路处理。

## 测试设计

### CommonTaskStreamPublisherTest

新增测试覆盖：

1. `executionId` 为空时，发布器自动生成非空 UUID，并发送到 Redis Stream producer。
2. `executionId` 已存在时，发布器不覆盖原值。
3. `commonTask` 或 producer 缺失时，保持现有错误处理语义。

### CommonTaskCommandStreamConsumerTest

新增或调整测试覆盖：

1. 同一 `commonNoticeUUID`、不同 `executionId` 时，完成上下文注册 key 不同。
2. 有 `executionId` 时，`JobLeaseService.getOrCreate` 收到的 `idempotencyKey` 使用 `executionId`。
3. 无 `executionId` 的历史消息仍使用旧 key：`common-task:{taskType}:{commonNoticeUUID}`。
4. 现有“终态跳过并 ACK”测试改为验证同一个 `executionId` 的重复消息才会跳过，避免把同页面二次点击误判为重复消息。

### CommonTaskRedisCompletionHandlerTest

新增或调整测试覆盖：

1. 完成处理器使用 `executionId` 构造 registry key，能找到消费者保存的上下文。
2. 无 `executionId` 时仍可使用旧 key 找到历史上下文。
3. 已有成功、失败、通知失败不 ACK、结果失败转终态等测试继续保留。

## 验收标准

1. 同一页面同一个 `commonNoticeUUID` 连续提交两次拼图任务，会创建两条不同 `stream_job_execution` 记录，第二次不会命中第一次的 `SUCCEEDED` 终态跳过执行。
2. Redis Stream 同一条消息重试时，不会创建新的执行批次，也不会重复执行业务逻辑。
3. WebSocket 通知仍携带原 `commonNoticeUUID`，前端现有页面过滤逻辑不需要改变。
4. 历史没有 `executionId` 的消息仍可被消费，不因字段缺失失败。
5. 相关单元测试通过，并且不回退已有 ACK、租约、真实终态和通知失败恢复语义。

## 风险与约束

1. 如果存在绕过 `CommonTaskStreamPublisher` 直接发送 `CommonTask` 的代码，可能无法自动生成 `executionId`。实施时需要用 `rg` 检查所有发布入口。
2. `CommonTaskCommandStreamConsumer` 和 `CommonTaskRedisCompletionHandler` 必须共享同一幂等键规则。若复制实现，需要测试锁定；若抽取工具方法，需要保持依赖方向清晰，避免 task 与 system 互相耦合。
3. 历史终态记录仍会阻止没有 `executionId` 的旧格式重复提交。新提交必须经过发布器生成 `executionId`，这是本设计的关键前提。
4. 不修改数据库唯一约束，因此同一个 `executionId` 不能被两个不同业务执行复用。当前由 UUID 生成，冲突风险可忽略。
