# 图形／统计上传限额与解析提速完成总结

## 结果摘要

图形／统计单文件上传的前端默认限制和后端六个业务处理入口统一为 **20,000,000 字节**：恰好达到边界允许，超过一个字节拒绝。后端表格插列改为按行下标直接替换，保留上传后整张表立即可编辑的行为。本地三个代码仓库已合入各自 `master`，完成构建、测试和后端启动关闭验收；尚未推送或部署。代表性大表的插列步骤明显加快；用户随后实测一份 250,000 行文件上传成功，耗时约 2.5 分钟。

用户随后手动验收发现两项问题：边界测试 XLSX 缺少附加文件的内容类型声明；成功上传大表后再次上传，会把上一次的整表放进普通表单字段，触发 Tomcat `maxPostSize`。测试文件已修正并复制到两个交付目录，前端已移除重复提交的表格内容并合入本地 `master`。用户实测 250,000 行文件成功显示可编辑表格，耗时约 2.5 分钟；修复后完整 HTTP 上传尚待用户复测。

用户再次实测 172,800 行文件的服务器等待约 1.7 分钟后，本轮继续修复共用 Excel 读取器对普通文本逐格抛数字解析异常的问题。修复已合入 `freedom-public/master`、安装到共享 Maven 仓库，并重新构建 `goto-manager.jar`。相同文件的 Windows Java 独立处理测量从 8.726 秒降到 6.467 秒；浏览器完整请求仍须用户手动启动新版后复测。

用户随后用图形侧栏上传精确 20,000,000 字节的 03 文件时，浏览器收到 HTTP 400，整条请求为 38,692,216 字节。已确认额外的约 18.7 MB 来自上一次上传的列去重值 `uploadFileInfo.map` 被放入 `data` 表单字段；本轮从上传请求副本中移除该字段，页面内列选项保留。前端修复已合入本地 `goto-web/master`，定向测试、ESLint 和生产构建通过；真实浏览器重复上传仍待用户复测。

## 原因与目标

用户在本地上传约 11 MB 的图形／统计文件时，浏览器等待后端响应约 8.7 分钟；当时直接使用的前端上传器默认限制为 30,000,000 字节，图形／统计后端入口没有对应业务限额。目标是前后端一致限制到 20,000,000 字节，并修复大表处理中的慢算法，继续支持整表编辑，以相同数据对关键步骤做旧版和新版实测。

第一次算法修复后，01 文件的完整请求仍由后端等待约 1.7 分钟。数据库 `sys_log` 记录对应上传为 104,444 毫秒，另一次采样为 113,309 毫秒；JFR 在请求线程工作期间记录约 182 万次异常，主要来自文本单元格被尝试构造为 `BigDecimal`。此次目标是在不改变数值与文本结果的前提下消除这类正常文本的异常开销，并交付可供手动重启的新版后端。

## 设计决策

前端修改直接上传组件的默认值，保留各调用方显式传入的限制；后端在图形／统计六类上传处理器的初始化初期调用共用的字节数校验，避免超限文件进入保存和解析。`HandsontableUtils.addColumn` 的旧实现每行调用 `body.indexOf(row)`，会对已解析整表重复搜索；改为整数下标遍历和替换，消除这一步的平方级扫描，并确保重复内容的行各自处理。不改变上传接口、文件格式或整表编辑流程，也不把基准测试中的单一步骤耗时当成整个 HTTP 请求耗时。

第二轮在 `NoModelSheetDataListener` 中以无异常字符扫描筛选可解析的十进制形式，再由原有 `BigDecimal` 完成最终转换；普通文本、空值及解析失败的值仍保留原对象。独立测量表明三次读取在非调试环境仅占数秒，因此本轮不改动整表响应结构和读取次数。用户的 IDEA 后端启用了调试代理，异常成本会被放大；实际 Debug 模式下的完整加速幅度须重新上传确认。

本轮图形侧栏返修针对服务器日志明确指出的 `data` 普通表单字段：已有前端修复只剔除 `handsontable`，遗漏了包含整列去重值的 `map`。在请求副本中同时剔除二者，比扩大 Tomcat 的通用表单字段上限更直接，且不改变 20,000,000 字节的文件大小边界或页面内表格、列选项。后端不需要重新构建。

## 偏差、风险与遗留

没有在受控新服务上完成真实登录的整条 11 MB 上传重测，无法证明浏览器等待的约 1.7 分钟已缩短到何值。用户实测 250,000 行文件上传约 2.5 分钟，说明完整链路仍有耗时；本次前端返修只解决连续上传时额外的表单体积及由此导致的失败，第二轮读取器修复才针对首次上传的后端异常开销。修复后的连续上传、两份边界文件以及 01 文件的完整 HTTP 耗时仍需用户在当前前端刷新页面后复测；本轮没有带认证的真实 HTTP 上传验收，因此不能把定向测试通过等同于用户页面已恢复。此前后端启动验收只验证服务和路由可用；本轮未修改后端，未重启或停止用户当前的 8808 服务。代码仅合入本地主分支，未推送、未部署。
