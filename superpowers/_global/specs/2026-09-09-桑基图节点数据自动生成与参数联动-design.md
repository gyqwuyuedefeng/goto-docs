# 桑基图节点数据自动生成与参数联动设计

## 背景与目标

桑基图当前配置两个输入文件：

- `edgesFile`（索引 0，边数据），包含起点、终点及属性等列名标记；
- `nodesFile`（索引 1，节点数据），包含节点名称、层级及节点属性等列名标记。

现状要求用户分别上传边数据和节点数据。本次改为只上传边数据：用户保存边数据列名标记后，系统异步调用 `gotoPlot::get_nodeslist_from_edges` 生成 `nodesFile.xlsx`，并把生成文件接入与普通上传相同的文件状态、表格刷新及参数联动流程。

本次同时完善桑基图参数联动：节点层级顺序决定标签对齐方式数量；边填充色是否显示由“填充色跟随节点”控制；节点数据上传入口隐藏但节点数据页签保留。最后仅修改桑基图 PlotGroup 模板中边填充参数的中文名称，不同步到 PlotType。

## 已核对的真实配置

从 `application-common-home.yml` 读取 home 环境数据库连接配置后，以只读方式核对数据库：

- `app_plot_group` 中桑基图组为 `id=15`、`folder_name=Sankey`；
- `app_plot_type` 中桑基图模板均使用 `GT_Sankey`，本次以其中一个模板核对参数结构；
- `edgesFile` 为索引 0，`nodesFile` 为索引 1；
- `nodeGroupOrder` 为 `moduleType=27`，来源配置指向节点数据的层级标记；
- `nodeLabelAlign` 为 `moduleType=13`，使用水平对齐字典；
- `colorFollowNode` 为布尔选择参数，值为 `TRUE/FALSE`；
- `edgeFillColor` 为颜色参数，当前中文名称为“填充色”。

相关数据字典已存在，不新增字典：水平对齐选项为 `left`、`right`、`center`。节点层级实际选项不来自固定字典，而是来自节点文件中被标记为层级列的数据去重结果。

## 服务边界

所有 R 调用必须位于 `task` 服务。`system` 服务不得直接连接 Rserve，也不得在保存列标记的 HTTP 请求中同步执行 R。

采用项目现有 Redis Stream 通用任务链路：

```text
浏览器保存边数据标记
  -> system 持久化边标记并生成 file-mark-edgesFile.xlsx
  -> system 发布桑基图节点生成 CommonTask
  -> task 消费任务并调用 gotoPlot::get_nodeslist_from_edges
  -> task 校验并整理 nodesFile.xlsx，更新 UserDraw 文件配置
  -> task 发布完成通知
  -> system 消费通知并通过 WebSocket 推送
  -> 浏览器刷新节点文件与参数联动
```

任务复用现有通用任务的执行账本、租约、重试、手动 ACK、完成通知和 WebSocket 最后一跳，不增加第二套消息协议。

## 后端任务模型与发布条件

在公共模块新增桑基图节点生成任务数据模型，并在 `TaskType` 增加独立任务类型。任务数据只携带当前闭环所需字段：

- 用户绘图 ID、绘图类型 ID、桑基图组 ID；
- R 可访问的边文件路径和节点输出路径；
- Java 可访问的节点输出路径；
- 节点文件索引与必要的文件设置标识。

R 参数明确生成：

```r
gotoPlot::get_nodeslist_from_edges(
  edgesFile = "<R 可访问的 Upload/edgesFile.xlsx>",
  fileName = "<R 可访问的 Upload/nodesFile.xlsx>"
)
```

边文件路径按需求使用上传目录中的 `edgesFile.xlsx`；保存标记生成的 `file-mark-edgesFile.xlsx` 仍供现有绘图参数流程使用，不替换本函数的输入语义。

`saveFileMarkSettings` 继续先完成既有边标记保存。仅当以下条件同时满足时发布节点生成任务：

1. 当前为用户绘图而不是示例模板；
2. `groupId=15`；
3. 当前保存的文件索引为 0，且文件名为 `edgesFile`；
4. 用户绘图、边文件和节点文件配置均有效；
5. 当前用户对该用户绘图具有既有访问权限。

发布成功后接口仍返回“标记保存成功”，同时携带任务已提交状态。若任务发布失败，边标记已经保存，接口明确返回节点生成任务提交失败，不伪装为全部成功。

## task 服务执行与并发控制

`task` 服务新增对应的消息处理器和专用 Stage：

1. 消息处理器校验任务数据并组装 R 调用；
2. 将任务加入现有 `CommonTaskThreadPool`；
3. 专用 Stage 在 R 成功后执行节点文件后处理；
4. 任务完成处理器沿用现有 Redis Stream 成功或失败通知。

线程池 Key 使用用户 ID、用户绘图 ID和任务类型组合。同一幅图连续保存边标记时，节点生成任务按队列串行执行，最终输出对应最后一次保存后的边文件状态，避免并发 R 任务交叉覆盖 `nodesFile.xlsx`。

每次任务均使用新的 `executionId`，允许用户重复保存并重新生成；同一条 Redis 消息仍由现有任务账本保证幂等。

## 节点文件后处理与持久化

R 成功返回后，专用 Stage 执行以下操作：

1. 校验 Java 侧 `nodesFile.xlsx` 存在且不是空文件；
2. 按普通上传规则确保首列存在 `GT_Selected`；
3. 重新查询最新的 `UserDraw`，按文件名和索引定位 `nodesFile` 设置；
4. 从生成文件重新读取 `headerInfoList`；
5. 所有节点列标记从未选择状态开始，不保留旧节点文件的标记；
6. 清除旧的节点标记衍生文件，避免继续使用旧 `file-mark-nodesFile.xlsx`；
7. 持久化新的节点文件设置；
8. 将节点文件索引和最新文件设置加入任务成功通知数据。

每次重新保存边标记都允许覆盖已有 `nodesFile.xlsx`。这是已确认行为；旧节点列标记也随之重置，等同于一次新的节点文件上传。

若 R 执行或后处理失败，边标记仍保留，旧节点配置不得被写成新成功状态。失败通过现有最终失败通知返回，用户可再次保存边标记触发重试。

## 前端异步回调

边数据的 `FileMark` 组件在提交保存请求前注册本页 `commonNoticeUUID` 的 WebSocket 回调，并随请求传给后端。收到桑基图节点任务成功通知后：

1. 校验通知任务类型、用户绘图 ID 和节点文件索引，忽略其他页面或其他任务消息；
2. 将最新 `headerInfoList` 和已上传状态写入 `plot.userDraw.fileSettings[1]`；
3. 重新计算列名及列值缓存；
4. 调用现有 `uploadFileModify`，以节点数据索引 1 执行与普通上传相同的参数联动；
5. 切换到“节点数据”结果页签并刷新该页 Handsontable；
6. 显示节点数据生成成功提示。

失败通知只显示明确错误，不把节点文件设为已上传。页面销毁时继续由现有 mixin 注销回调，避免跨页面残留。

为避免普通上传与自动生成出现两套行为，文件成功后的公共状态更新、列缓存刷新和 `uploadFileModify` 调用将收敛为可复用方法；普通上传入口和桑基图异步成功入口调用同一方法。

## 节点数据上传入口

`PlotSidePanel` 的上传文件区域仍保留完整 `fileSettings` 数据，但对 `groupId=15` 且文件名为 `nodesFile` 的上传卡片不渲染。因此：

- 用户只能上传边数据；
- 节点数据不会出现上传按钮；
- `PlotResultCanvas` 仍根据完整 `fileSettings` 渲染“节点数据”页签；
- 节点数据生成后可以正常查看、编辑表格和保存列名标记。

该规则只作用于桑基图节点文件，不影响其他图组或桑基图边文件。

## 参数联动

### 节点层级与标签对齐

现有公共 `moduleType=27` 标记联动负责从节点数据的层级标记列读取并去重，生成 `nodeGroupOrder.list`。桑基图专属逻辑在公共更新完成后执行：

- `nodeLabelAlign` 的选项个数严格等于去重后的层级个数；
- 不再使用“最少两个”的旧兜底；
- 层级为 0 个时，对齐列表为空；
- 层级新增、减少或重新排序后，对齐列表同步调整；
- 能按既有索引保留的已有对齐值继续保留，新增项使用参数组件的既有默认值。

首次加载、节点文件自动生成、节点标记保存、节点内容保存和节点文件删除均执行同一刷新规则。

### 边填充色跟随节点

`colorFollowNode` 使用公共布尔解析，兼容 `TRUE`、`T` 和布尔值：

- 为“是”时，隐藏 `edgeFillColor`；
- 为“否”时，显示 `edgeFillColor`；
- 首次加载立即校正；
- 用户切换参数时立即校正；
- 条件撤销后恢复显示，不保留旧的错误隐藏状态。

本次只改变参数可见性，不修改 `edgeFillColor` 当前保存的颜色值。

## PlotGroup 模板名称修改

功能和端到端验收完成后，通过现有管理端/API 更新桑基图 PlotGroup（`id=15`）模板参数，将：

```text
edgeFillColor.name: 填充色 -> 填充颜色
```

仅更新 PlotGroup 的模板参数，不调用同步到全部 PlotType 的操作，也不直接使用数据库客户端写入。更新后重新只读查询 PlotGroup 和一个 PlotType，确认 PlotGroup 已修改而 PlotType 仍保持原名称。

## 测试与验收

### 后端测试

- `system`：桑基图边标记保存后发布正确任务；非桑基图、节点标记保存、示例模板不发布；路径同时包含 Java 本地视图和 R 远端视图；发布失败有明确响应。
- `common`：新任务 DTO 能在 Redis Stream JSON 往返；`CommonTask.simpleData` 能将成功通知所需数据传给前端。
- `task`：消息处理器构造正确的 `gotoPlot::get_nodeslist_from_edges` 调用；任务数据 Map 能转换为新 DTO；专用 Stage 校验输出、增加 `GT_Selected`、重置节点标记、更新用户绘图文件设置；失败不写成功状态。
- 并发语义：同一用户绘图使用同一个线程池 Key，不同用户绘图互不串行阻塞。

### 前端单元测试

- 桑基图隐藏节点数据上传卡片，但保留节点结果页签；
- 自动生成成功执行与普通上传一致的文件状态和参数回调；
- 成功通知刷新节点页签和表格，失败通知不设置已上传；
- 节点层级去重后，`nodeLabelAlign` 数量严格相等，包括 0、1、2 和多层级；
- `colorFollowNode` 的真、假及首次加载显隐行为；
- 其他图组不受影响。

### 本地端到端验收

按项目规范使用动态空闲端口启动 `task`、`system` 和 `goto-web`，不复用已有服务。后端使用 `home` profile，`system` 验收启动参数包含 `-Denv=local`。

Playwright 验收期间严格临时复制微信公众号验证码登录页，使用本地验证码 `666888`；无论成功或失败均恢复原始 `login.vue`，校验 SHA-256 和 Git 差异。验收覆盖：

1. 桑基图仅显示边数据上传按钮，节点数据页签存在；
2. 上传边数据并保存必需标记后收到异步完成通知；
3. `nodesFile.xlsx` 自动生成并显示在节点数据页；
4. 再次保存边标记会覆盖节点文件并清空旧节点标记；
5. 标记节点层级后，层级顺序去重且标签对齐数量一致；
6. 切换“填充色跟随节点”正确隐藏和显示“填充颜色”；
7. 页面刷新后上述状态仍正确；
8. 任务失败时提示明确且不会伪造节点文件成功状态。

验收结束后通过受控终端关闭本次启动的全部服务并确认端口释放。

## 非目标

- 不在 `system` 或前端直接调用 R；
- 不修改 `gotoPlot::get_nodeslist_from_edges` 的 R 实现；
- 不新增或修改数据字典；
- 不改变其他图组的文件上传或参数联动；
- 不允许用户手工上传节点数据；
- 不保留重新生成前的节点列标记；
- 不把 PlotGroup 的“填充颜色”名称同步到任何 PlotType；
- 不借本次任务重构通用 Redis Stream、线程池、文件上传或 WebSocket 架构。
