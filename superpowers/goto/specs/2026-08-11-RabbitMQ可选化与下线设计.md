# RabbitMQ 可选化与下线设计

## 目标

在不改变 goto 当前业务行为的前提下，使 `goto-manager` 与 `goto-task` 不再携带 RabbitMQ 客户端依赖、不再加载 RabbitMQ Bean，也不再需要可用的 RabbitMQ 服务。

当前用户绘图任务、取消任务、通用任务、示例数据任务及其通知链路继续使用 Redis Stream；登录、接口限流和防抖继续使用 Redis。

## 非目标

- 不调整 Redis Stream 的消息协议、Stream Key、消费者组、ACK、重试或死信逻辑。
- 不新增消息中间件抽象层或新的公共模块。
- 不修改数据库结构和业务接口。
- 不强制删除 `freedom-public` 中可能被工作区外项目复用的 RabbitMQ 工具 API；这些 API 改为显式选择的可选能力。

## 当前问题

`goto` 自身已经删除 RabbitMQ 业务生产者和消费者，但仍存在以下耦合：

1. `goto/common` 直接依赖 `spring-boot-starter-amqp`。
2. `eladmin-common` 的 `LimitAspect` 强制注入 `RabbitTemplate`，即使当前限流和防抖只使用 Redis。
3. `common-utils`、`common-thread`、`common-ttl-log` 包含 RabbitMQ 专用类，并通过普通 Maven 依赖将 AMQP 客户端传递给 goto。
4. `common-r`、`common-thread-r` 没有 RabbitMQ 源码调用，却仍声明 AMQP 依赖。
5. goto 的运行配置、测试、备份和历史文件仍保留 RabbitMQ 内容。

如果只删除 `goto/common` 的 AMQP 依赖，`LimitAspect`、`RabbitCommonConfig` 和 `RabbitTemplateInitializer` 会因为缺少 RabbitMQ 类型或 Bean 导致编译或启动失败。

## 方案选择

采用“核心彻底解耦、共享 RabbitMQ 能力可选加载”的方案。

- goto 最终运行制品完全不包含 RabbitMQ 客户端。
- 当前正在使用的限流核心彻底移除 RabbitMQ 依赖，不能通过条件注解整体关闭。
- 可能被其他项目使用的 RabbitMQ 公共工具保留，但其 Maven 依赖设为 optional，并仅在 AMQP 类存在时创建相关 Spring Bean。
- 不新建 `common-rabbit` 模块，避免为当前下线需求扩大架构范围。

## `freedom-public` 设计

### `eladmin-common`：限流核心彻底解耦

`LimitAspect` 同时承载当前有效的 `@RateLimit` 和 `@Debounce`。如果直接对整个 Aspect 使用 `@ConditionalOnClass(RabbitTemplate)`，没有 RabbitMQ 时 Redis 限流也会被关闭，因此该模块不采用条件加载。

调整内容：

- `LimitAspect` 只注入 `RedisTemplate`。
- `LimitHandler` 删除 `RabbitTemplate` 字段和构造参数。
- `DebounceHandler`、`RateLimitHandler`、`TotalLimitHandler` 构造器同步删除 `RabbitTemplate` 参数。
- `TotalLimitHandler` 删除 `RABBIT_MQ` 分支，保留 Redis 集合计数逻辑。
- `LimitDataSourceStrategy` 删除 `RABBIT_MQ` 枚举值；`TotalLimit` 继续默认并只支持 Redis。
- `eladmin-common/pom.xml` 删除 `spring-boot-starter-amqp`。

当前 goto-software 工作区内不存在 `@TotalLimit` 调用，也不存在 `RABBIT_MQ` 策略调用，因此不会改变当前业务行为。

### `common-utils`：RabbitMQ 工具可选化

- `spring-boot-starter-amqp` 设置为 Maven optional 依赖，供本模块编译，但不再传递给 goto。
- `RabbitCommonConfig` 增加类名字符串形式的条件：

```java
@ConditionalOnClass(name = {
        "org.springframework.amqp.rabbit.core.RabbitTemplate",
        "org.springframework.amqp.core.Queue"
})
```

- 条件放在独立的 `RabbitCommonConfig` 配置类上，保证缺少 AMQP 类时 Spring 在加载 `@Bean` 方法返回类型前跳过整个配置。
- `RabbitMQUtils` 保留为非 Spring 工具类；需要它的外部项目必须自行显式引入 AMQP starter。

### `common-ttl-log`：Rabbit 消息追踪可选化

- AMQP starter 设置为 optional。
- `MessageConverterConfig` 和 `RabbitTemplateInitializer` 使用类名字符串形式的 `@ConditionalOnClass`。
- `RabbitTemplateInitializer` 使用 `ObjectProvider<RabbitTemplate>` 获取模板；即使调用方引入了 AMQP 类库但没有创建 `RabbitTemplate` Bean，也不会启动失败。
- Web 请求 TraceId、MDC、异步线程上下文传播等非 Rabbit 功能不改动。

### `common-thread`：消费者基类可选化

- AMQP starter 设置为 optional。
- `BaseConsumer` 不是 Spring Bean，且当前工作区内没有有效子类，因此保留源码即可；没有 AMQP 依赖的 goto 不会加载它。
- 外部项目若仍继承 `BaseConsumer`，必须显式引入 AMQP starter。

### `common-r` 与 `common-thread-r`

两个模块没有 RabbitMQ 源码引用，直接删除 POM 中的 AMQP 依赖。

## `goto` 设计

### Maven 依赖

- 从 `goto/common/pom.xml` 删除 `spring-boot-starter-amqp`。
- `system` 和 `task` 继续通过 `goto-common`、Redis Stream starter 使用 Redis，不新增替代依赖。

### 运行配置

删除以下配置：

- `system/src/main/resources/config/application.yml` 中的 `spring.rabbitmq`。
- `task/src/main/resources/application.yml` 中的 `spring.rabbitmq`。
- `common/src/main/resources/application-common-home.yml` 和 `application-common-public.yml` 中的连接信息。
- `user-draw.rabbitmq.enabled`。

删除配置后不再需要 `spring.rabbitmq.dynamic=false` 或 `management.health.rabbit.enabled=false`，因为最终运行时不存在 Rabbit 自动配置和 Rabbit 健康指示器。

### Java 与测试

- `UserDrawTaskProperties` 删除 RabbitMQ 配置字段、内部类和 `useRabbitMQ()`，保留 Redis Stream 配置。
- `LimitTest` 删除 `RabbitTemplate` Mock，并使用新的纯 Redis `LimitAspect` 构造器。
- 修正仍把 Redis Stream 描述成 RabbitMQ 的注释、局部变量和日志文案。

### 历史残留

以下内容不参与当前运行，随本次清理删除或清除其中的 RabbitMQ 内容：

- `task/src/main/java/com/freedom/util/DoUserDrawTaskBackup.java`
- `task/src/main/java/com/freedom/util/DoUserDrawTaskBackup1.java`
- `a-rabbitmq/rabbit_rabbitmq_2024-6-6.json`
- `.backup` 中的 RabbitMQ 配置段

Redis Stream 迁移说明中用于解释历史背景的少量文字可以保留，但失效的 Javadoc 类链接必须改成普通文字，避免继续引用已删除类型。

## 运行行为

调整后的消息流保持不变：

1. system 将用户绘图、取消、通用任务和示例数据任务写入 Redis Stream。
2. task 使用 `@StreamListener` 消费任务并执行业务线程池逻辑。
3. task 将完成、失败和进度通知写入 Redis Stream。
4. system 消费通知并通过现有 WebSocket 推送浏览器。

RabbitMQ 下线不会触发替代或降级分支，因为当前业务链路已经直接以 Redis Stream 为唯一实现。

## 兼容性与错误处理

- goto 缺少 AMQP 类库时，条件化的共享 Rabbit 配置必须完全跳过，不能产生 `ClassNotFoundException`、`NoClassDefFoundError` 或缺少 Bean 的启动错误。
- 外部项目显式引入 AMQP starter 时，保留的 Rabbit 公共工具仍可创建相应 Bean。
- Redis 不可用时维持现有失败行为，本次不改变重试、异常传播或健康检查策略。
- 当前配置中出现过的 RabbitMQ 凭据在服务下线后应视为已暴露凭据处理；若仍有效，需要在服务器侧撤销或轮换。

## 测试设计

### 失败检查

实现前建立以下可重复检查，并确认它们在当前代码上失败：

- goto POM 和有效运行配置不得包含 RabbitMQ 依赖或连接配置。
- goto 有效 Java 代码不得导入 Spring AMQP 或 RabbitMQ Client。
- 限流核心不得引用 `RabbitTemplate` 或 `RABBIT_MQ`。
- 使用过滤 AMQP 类的 Spring 测试类加载器加载共享配置时，ApplicationContext 不得失败，也不得创建 Rabbit Bean。

### 回归检查

- `LimitTest` 验证纯 Redis `LimitAspect` 仍可完成接口限流代理调用。
- `eladmin-common` 的 Redis 限流、防抖和 TotalLimit 测试保持通过。
- Redis Stream 生产者、消费者及通知测试保持通过。
- `freedom-public` 受影响模块和 goto 三个模块完成编译测试。

### 最终制品检查

`goto-manager.jar` 和 `goto-task.jar` 不得包含：

- `spring-rabbit-*.jar`
- `spring-amqp-*.jar`
- `amqp-client-*.jar`

RabbitMQ 完全不可访问时，system 和 task 必须能够启动；验证后关闭本次启动的应用。

## 验收标准

1. goto 的 Maven 依赖树和最终可执行 JAR 不包含 RabbitMQ/AMQP。
2. goto 的有效配置不包含 RabbitMQ 地址、端口、账号、密码或虚拟主机。
3. system、task 在没有 RabbitMQ 服务时启动成功。
4. 登录、限流、防抖保持 Redis 实现并正常工作。
5. 用户绘图提交与取消、通用任务、示例数据任务和 WebSocket 通知保持 Redis Stream 实现并正常工作。
6. freedom-public 中保留的可选 Rabbit 工具不会在缺少 AMQP 类库时创建 Bean 或导致启动失败。

## 风险与回滚

- 主要风险是共享模块的可选依赖或条件配置不完整，导致缺少 AMQP 类时发生类加载失败。
- 次要风险是工作区外项目依赖过去的传递式 AMQP 依赖；这些项目需要改为显式声明 starter。
- 两个仓库必须按 `freedom-public` 先安装、goto 后构建的顺序验证。
- 服务器侧先停止 RabbitMQ 并保留数据与安装包，待业务验证稳定后再卸载，以便必要时快速恢复。
