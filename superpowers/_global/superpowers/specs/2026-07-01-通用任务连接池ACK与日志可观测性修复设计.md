# 通用任务连接池 ACK 与日志可观测性修复设计

## 背景

2026-07-01 测试 `POST /api/tools/submit_merge_image_task` 时，`goto/task` 与 `goto/system` 同时出现数据库连接获取失败：

- `HikariPool-1 - Failed to validate connection ... No operations allowed after connection closed`
- `HikariPool-1 - Connection is not available, request timed out after 2026ms (total=5, active=0, idle=5, waiting=0)`
- `Could not open JPA EntityManager for transaction`

`goto/task` 的异常发生在 `CommonTaskCommandStreamConsumer` 调用 `JobLeaseService.getOrCreate` 创建/读取 Job Ledger 时。`goto/system` 的异常发生在异步保存接口日志时。两边报错时间一致，且都是 Hikari 校验已关闭 idle 连接失败后在约 2 秒连接超时。

同一请求包含 `data:image/jpeg;base64,...` 形式的大图参数。当前日志服务已把超长参数截断到 4000 字符，但截断发生在构造日志参数之后，仍会在日志链路中处理大体积 base64 文本。

## 目标

1. 避免 stale MySQL idle 连接导致 task/system 在短时间内同时无法获取连接。
2. `JobLeaseService.getOrCreate` 因数据库连接失败时，Redis Stream 消息不能被 ACK，必须留给 PEL/重试恢复。
3. 手动 ACK 场景下，日志能区分 listener 返回、已 ACK、未 ACK，避免把 `Message processed successfully` 误读为业务消息已确认。
4. 接口日志不写入完整 base64 图片参数，降低日志链路内存、序列化和数据库写入压力。
5. 用回归测试固定 ACK 语义，防止后续再次把 ledger 创建失败误判为可 ACK。

## 非目标

1. 不改变通用任务真实完成后再写终态、通知、ACK 的总体方案。
2. 不在本轮引入新的队列或恢复 RabbitMQ。
3. 不改造 `stream_job_execution` 表结构。
4. 不解决所有历史 Hikari 配置差异，只处理 task/system 当前暴露的连接池风险。
5. 不把日志参数完全删除，仍保留可排查的结构化摘要。

## 当前事实

- `goto/task` 与 `goto/system` 的 Hikari `connection-timeout` 均为 `2000` 毫秒，`validation-timeout` 为 `1000` 毫秒。
- 两个服务的 Hikari `minimum-idle` 为 `5`。报错时池状态为 `active=0, idle=5`，说明不是业务连接泄漏，而是 idle 连接已被关闭且池无法在 2 秒内完成替换。
- `CommonTaskCommandStreamConsumer` 在 listener 中先调用 `JobLeaseService.getOrCreate`，再认领租约、转换参数并提交线程池。
- `getOrCreate` 是 `@Transactional` 方法。数据库连接获取失败时，异常会发生在事务开启阶段，方法体可能尚未执行。
- 当前 listener 捕获异常后，如果 `jobId == null` 会在 finally 中调用 `context.ack()`，这会把 ledger 创建失败的消息确认掉。
- `StreamConsumerContainer` 在 manual ACK 场景中只要 listener 方法返回就会输出 `Message processed successfully`，该日志不代表 `XACK` 已执行。
- `LogServiceImpl` 会把过长参数截断至 4000 字符，但对 base64 图片参数没有结构化脱敏或替换。

## 根因判断

本次 JDBC 异常的直接原因是 Hikari 池中保留了被 MySQL 或网络层关闭的 idle 连接，服务取连接时需要逐个校验并丢弃这些连接。当前 `connection-timeout=2000ms` 太短，导致池还没完成连接替换就向业务层抛出 `SQLTransientConnectionException`。

这不是拼图任务或 R 运行时本身的错误。`goto/task` 失败点在 Job Ledger 创建阶段，尚未进入 R 任务执行。`goto/system` 的接口日志保存失败是同一个数据库连接池问题的连带表现。

同时，`CommonTaskCommandStreamConsumer` 对 `jobId == null` 的兜底 ACK 与长任务可靠性设计冲突。数据库短暂不可用时，消息应该保留在 PEL 中等待恢复，而不是被确认并丢失执行机会。

## 方案

采用完整修复方案：连接池配置、ACK 语义、日志降噪和 ACK 可观测性一起处理。

### Hikari 配置

同步调整 `goto/task` 与 `goto/system` 的连接池配置：

```yaml
spring:
  datasource:
    hikari:
      connection-timeout: 10000
      validation-timeout: 3000
      max-lifetime: 240000
      keepalive-time: 60000
```

原则：

- `connection-timeout` 需要覆盖校验 stale idle 连接并创建新连接的时间。
- `validation-timeout` 不应大到拖垮请求，但要大于短暂网络抖动。
- `max-lifetime` 必须短于 MySQL、代理或 NAT 的连接回收时间。
- `keepalive-time` 用于在连接长期 idle 前主动探活，降低整池 stale 的概率。

如果实际 MySQL `wait_timeout` 明确更短，则实现时按 `max-lifetime < wait_timeout` 重新取值。

### ACK 语义

`CommonTaskCommandStreamConsumer` 增加明确的 ledger 创建失败分支：

```text
getOrCreate 抛数据库/事务/连接异常
→ 记录错误
→ 不写终态
→ 不通知
→ 不 ACK
→ 让消息留在 PEL
```

保留以下 ACK 场景：

- 消息结构无效且无法恢复，例如 `commonTask == null`。
- `commonTask.data == null` 且按现有策略视为无效消息。
- job 已处于终态，重复投递时直接 ACK。
- 后台真实完成后，完成处理器成功写入 `SUCCEEDED` 或 `FAILED_FINAL` 并发布通知。

不 ACK 场景：

- `JobLeaseService.getOrCreate` 获取数据库连接失败。
- `JobLeaseService.acquire` 认领失败，等待 PEL/租约恢复。
- 提交线程池前发生未知基础设施异常且未能创建可靠 Job Ledger。
- 后台完成处理器写账本或发通知失败。

### Stream 手动 ACK 日志

`StreamConsumerContainer` 调整 manual ACK 日志语义：

- listener 方法正常返回：输出 `manual ACK listener returned`。
- `MessageContext.isAcked() == true`：输出 `manual ACK completed`。
- `MessageContext.isAcked() == false`：输出 `manual ACK pending`。

保留 auto ACK 场景的现有成功日志，但手动 ACK 场景不再只用 `Message processed successfully` 表达。

### 日志参数降噪

`LogServiceImpl` 在截断前先对参数做 base64 图片替换。替换规则：

```text
data:image/{type};base64,{payload}
→ data:image/{type};base64,<omitted length={payloadLength} sha256={first16}>
```

要求：

- 不保留完整 base64。
- 保留媒体类型、原始 payload 长度和短 hash，便于排查是否同一张图片。
- 替换后仍走现有 4000 字符截断逻辑，防止其他长参数进入数据库。
- 脱敏失败不能影响主业务请求，也不能让日志保存抛出新的运行时异常。

## 数据流

### 正常提交

```text
system 接收 HTTP 请求
→ 日志参数替换 base64 并截断
→ system 上传/落盘图片并发布 Redis Stream 命令
→ task listener 收到消息
→ getOrCreate 成功
→ acquire 成功
→ 提交后台任务
→ listener 返回，不 ACK
→ 后台真实完成
→ 写终态
→ 发布通知
→ ACK
```

### 数据库短暂不可用

```text
task listener 收到消息
→ getOrCreate 开启事务时无法获取连接
→ listener 记录异常
→ manual ACK pending
→ 消息留在 PEL
→ 数据库恢复后由重试/claim 机制重新处理
```

### 日志保存失败

```text
system HTTP 主请求继续走提交链路
→ async 日志保存如果仍因连接池问题失败，只记录异步错误
→ 不影响 Redis Stream 命令发布语义
```

## 测试设计

### goto/task

新增或调整 `CommonTaskCommandStreamConsumerTest`：

- `getOrCreate` 抛 `CannotCreateTransactionException` 时，不调用 `context.ack()`。
- `getOrCreate` 抛数据库连接类异常时，不调用通知发布，不写终态。
- 空消息/空 data 等既有不可恢复消息仍按现有策略 ACK。
- 提交线程池成功后 listener 返回仍不 ACK。
- 后台完成处理器成功写终态并通知后 ACK。

### freedom-public/redis-stream-spring-boot-starter

新增 `StreamConsumerContainer` 单元测试或轻量行为测试：

- manual ACK 且 listener 未 ACK：日志/状态为 pending，不自动 ACK。
- manual ACK 且 listener 已 ACK：日志/状态为 completed。
- auto ACK 继续保持原行为。

### freedom-public/eladmin-logging

新增 `LogServiceImpl` 参数处理测试：

- 单个 `data:image/jpeg;base64,...` 被替换为摘要。
- 多个图片字段都被替换。
- 非图片 base64 或普通字符串不被误删。
- 替换后超过 4000 字符仍被截断。

### 配置验证

启动 task/system 后确认：

- Hikari 配置生效。
- stale idle 连接场景下服务能丢弃旧连接并创建新连接。
- 不再出现 2 秒连接超时导致的整池不可用现象。

## 风险与缓解

- `connection-timeout` 变长会让真实数据库不可用时请求等待更久。缓解：仅提高到 10 秒，并依赖上层异步任务快速返回。
- `keepalive-time` 会增加少量数据库探活流量。缓解：60 秒间隔对当前池大小影响较小。
- `getOrCreate` 失败不 ACK 会让 PEL 中保留消息。缓解：这是预期的至少一次投递语义，应通过 PEL 恢复机制和监控处理。
- base64 替换正则若过宽可能误伤普通参数。缓解：只匹配 `data:image/...;base64,` 前缀。
- 手动 ACK 日志调整可能影响依赖旧日志文本的排查脚本。缓解：保留 messageId、stream、group、consumer 等核心字段。

## 验收标准

1. 重放本次 `submit_merge_image_task` 请求时，task 不再在 `getOrCreate` 阶段因 stale idle 连接立即失败。
2. 模拟 `getOrCreate` 抛连接异常时，Redis Stream 消息不 ACK。
3. manual ACK 场景日志能明确看到 `completed` 或 `pending`。
4. system 日志中不再出现完整 `data:image/jpeg;base64,...`。
5. 相关单元测试通过，且不破坏 2026-06-30 真实终态方案的既有测试。
