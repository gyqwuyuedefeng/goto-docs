# 通用任务执行批次幂等修复 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `hybrid-subagent-driven-development` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为通用任务引入每次提交唯一的 `executionId`，让同一页面重复点击一定创建新的后台执行，同时保留 Redis Stream 重试幂等、租约、终态和 ACK 语义。

**Architecture:** 当前 Codex 会话作为 controller、reviewer、planner 和用户决策入口；DeepSeek 通过 `codex-dp-exec` 在隔离 worktree 中按任务实现。`goto/common` 扩展 `CommonTask` 执行批次字段，`goto/system` 在统一发布器兜底生成批次 ID，`goto/task` 统一消费者和完成处理器的幂等键规则。

**Tech Stack:** Java 17, Spring Boot 3.3.4, Maven 3.6.3, JUnit 5, Mockito, AssertJ, Redis Stream starter, codex-dp-exec.

## 字段/接口/约束映射

### 字段职责

```text
CommonTask.commonNoticeUUID
  含义：前端页面通知路由。
  生命周期：同一页面可复用。
  下游：system 通知消费者、前端 WebSocket 消息过滤、下载 taskId 场景。

CommonTask.executionId
  含义：后台执行批次 ID。
  生命周期：每次提交应唯一；同一 Redis Stream 消息重试时保持不变。
  下游：task 消费者 Job Ledger idempotencyKey、完成处理器 registry key。
```

### 幂等键规则

新消息：

```text
idempotencyKey = common-task:{taskType}:{executionId}
businessId     = commonNoticeUUID
```

历史消息兼容：

```text
如果 executionId 为空：
  idempotencyKey = common-task:{taskType}:{commonNoticeUUID 或 no-uuid}
```

注册表 key：

```text
registryKey = group:common_task_service:{idempotencyKey}
```

### 可靠性约束

- `CommonTaskStreamPublisher` 是 `executionId` 兜底生成入口。
- `CommonTaskCommandStreamConsumer` 和 `CommonTaskRedisCompletionHandler` 必须使用同一套幂等键规则。
- 不修改 `stream_job_execution` 表结构。
- 不修改唯一约束 `consumerName + idempotencyKey`。
- 不修改前端 `commonNoticeUUID` 过滤协议。
