# Hybrid 写计划技能设计

## 背景

现有 `superpowers:brainstorming` 在 spec 通过后固定进入 `superpowers:writing-plans`。`writing-plans` 已经可以在计划交接时列出 Hybrid、Original Subagent 和 Inline 三种执行方式，但它生成的计划仍是通用实施计划，不强制包含 Hybrid Subagent-Driven 执行需要的 `task_id`、worktree 绑定、DeepSeek prompt 上下文、run 目录检查、controller 审核门禁和恢复规则。

当前用户的主要工作流是 GPT-5.5 作为 controller/reviewer，DeepSeek 通过 `codex-dp-exec` 作为实现器。为了减少每次人工改写计划的成本，需要新增一个专门编写 Hybrid-ready implementation plan 的 skill，并让 brainstorming 在 spec 通过后允许用户选择使用 Hybrid 版写计划或原版写计划。

## 目标

- 新增 `hybrid-writing-plans` skill，专门把已批准 spec 写成 Hybrid-ready 实施计划。
- 修改 `superpowers:brainstorming` 的后续流程，使 spec 通过后不再固定调用 `writing-plans`，而是让用户选择计划编写方式。
- 保留原版 `superpowers:writing-plans`，用户仍可选择普通实施计划。
- Hybrid 版计划默认面向 `hybrid-subagent-driven-development` 执行。
- Hybrid 版计划必须包含 `codex-dp-exec` 所需的任务标识、worktree、报告格式、状态检查和恢复规则。

## 非目标

- 不修改 `superpowers:subagent-driven-development` 原版执行 skill。
- 不让 DeepSeek 参与设计、计划决策或最终审核。
- 不把所有计划都强制写成 Hybrid 计划；用户仍可选择原版 `writing-plans`。
- 不实现新的调度器或替代 `codex-dp-exec`。
- 不改变 brainstorming 的 spec 评审门禁；spec 仍需用户确认后才能进入写计划阶段。

## 方案选择

采用“新增 Hybrid 写计划 skill + 修改 brainstorming 分流”的方案。

spec 通过后的流程改为：

```text
brainstorming
  -> 写 spec
  -> spec 自审
  -> 用户 review spec 通过
  -> 询问计划编写方式
     1. Hybrid Writing Plans（推荐）
     2. Original Writing Plans
  -> 根据用户选择调用对应 skill
```

这个方案保持原版 `writing-plans` 的通用语义，同时给 Hybrid 工作流一套更严格的计划格式。

## 新 skill：hybrid-writing-plans

建议路径：

```text
/home/gyq/.agents/skills/hybrid-writing-plans/SKILL.md
```

建议 frontmatter：

```yaml
---
name: hybrid-writing-plans
description: Use when writing implementation plans that must be executed with a GPT-5.5 controller/reviewer and DeepSeek through codex-dp-exec
---
```

该 skill 的职责是从已批准 spec 生成 Hybrid-ready plan。它不是执行 skill，不能调用 `codex-dp-exec`，不能修改业务代码。

## Hybrid-ready Plan 要求

计划头部必须声明：

```markdown
> **For agentic workers:** REQUIRED SUB-SKILL: Use `hybrid-subagent-driven-development` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
```

计划必须包含以下章节：

- `执行前上下文`
- `Hybrid Subagent-Driven 执行约定`
- `字段/接口/约束映射`，按任务需要出现
- `文件结构`
- `Task 0: 工作区核查`
- 多个可独立派发的实现 Task
- 最终联调验收 Task
- `Hybrid readiness checklist`

每个实现 Task 必须包含：

- 固定 ASCII `task_id`，例如 `task-003-firelm-backend-tracking-core`。
- 执行方式：
  - `controller inline`
  - `DeepSeek implementer`
  - `DeepSeek implementer + controller重点复核`
- `--cd <worktree>` 对应的明确 worktree 路径。
- 允许修改的文件列表。
- 禁止修改的文件或行为。
- 完整任务上下文，不能依赖当前对话历史。
- 测试命令和预期结果。
- 提交命令，commit 信息必须符合项目规则。
- `BLOCKED`、`NEEDS_CONTEXT`、`DONE_WITH_CONCERNS` 的处理要求。

计划必须包含统一调用模板：

```bash
/home/gyq/.local/bin/codex-dp-exec \
  --cd <task-worktree> \
  --prompt-file <prompt-file> \
  --task-id <task-id> \
  --controller-id <codex1-or-codex2> \
  --output-last-message <report-file>
```

每个 DeepSeek prompt 必须要求最终报告包含：

```text
status: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
changed_files: 本任务改动的文件列表
commits: 本任务产生的 commit hash，没有提交时说明原因
tests: 实际运行的测试命令和结果
concerns: 风险、未验证项或需要 controller 判断的问题
```

## Controller 审核门禁

Hybrid 计划必须写明 controller 每个 task 后的审核顺序：

1. 检查 `status.json`、`heartbeat.json`、`stdout.log`、`stderr.log`、`report.md`、`exit_code`。
2. 检查 implementer report。
3. 检查 `git diff` 和 changed files。
4. 检查测试输出。
5. 先做规格符合性审查。
6. 规格符合后再做代码质量审查。
7. 两轮审查都通过后才勾选 task 完成。

如果 run 是 `interrupted`，controller 必须先审查当前 `git diff`，再决定保留改动继续补完、重新派发 recovery run，或升级给用户确认。

## Brainstorming 修改点

修改文件：

```text
/mnt/g/Obsidian/skill/superpowers/skills/brainstorming/SKILL.md
```

需要把“terminal state is invoking writing-plans”改为“terminal state is selecting a plan-writing skill”。

在用户确认 spec 后，提示：

```text
Spec approved. Choose plan-writing mode:

1. Hybrid Writing Plans - writes a Hybrid-ready plan for GPT-5.5 controller + codex-dp-exec implementer.
2. Original Writing Plans - writes the normal superpowers implementation plan.

Which approach?
```

如果用户选择 Hybrid，调用 `hybrid-writing-plans`。如果用户选择 Original，调用 `superpowers:writing-plans`。

## 旧计划兼容

`hybrid-writing-plans` 也可以用于旧计划的改写，但这属于单独用法：

- 输入：已有普通 implementation plan。
- 输出：Hybrid-ready plan。
- 必须补齐固定 `task_id`、worktree、执行方式、prompt 报告格式、controller 审核门禁和恢复规则。

旧计划如果 task 太大、路径过期、测试命令缺失或依赖旧对话历史，必须先返回需要改写的问题清单，不能假装可直接 Hybrid 执行。

## 验收标准

- `hybrid-writing-plans` skill 可以通过 skill validator。
- brainstorming 的 spec 后续流程不再只允许 `writing-plans`。
- spec 通过后会列出 Hybrid Writing Plans 和 Original Writing Plans 两个计划编写选项。
- Hybrid 版计划包含固定 ASCII `task_id`、worktree、可编辑范围、测试命令、报告格式和 controller 审核门禁。
- 原版 `writing-plans` 仍可被用户选择。
- 不修改原版 `superpowers:subagent-driven-development`。
- 不修改现有 `codex-dp` alias/function。

## 风险与约束

- 如果直接修改 `writing-plans`，会污染通用计划语义，因此本设计选择新增 skill。
- 如果 brainstorming 仍写死只调用 `writing-plans`，用户容易忘记切换 Hybrid 计划模式，因此必须修改 brainstorming 的终点说明。
- Hybrid 计划更长，token 成本更高；但它换来的是 DeepSeek implementer 可独立执行和 GPT controller 可审计恢复。
- 计划中的代码片段仍需与代码现状匹配；如果 spec 过旧或项目结构变化，Hybrid 写计划阶段必须先提示需要刷新上下文。
